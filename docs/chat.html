Chat with the agent

You give the agent a task in a chat, and it does the work in the workspace: it reads and edits files, runs commands, installs packages and commits with git. Everything it runs happens inside the workspace's jail, which can reach the internet but not your machine or your network. Your model provider key stays with the Echo server and never reaches the jail.

There is no chat window in the browser yet, so you chat through the API with curl. The examples assume Echo is at http://localhost:8000, $ECHO holds your session cookie (see Signing in), you have a workspace id from the Workspaces page, and you added a key on the Keys page.

Start a chat

curl -b "$ECHO" -X POST http://localhost:8000/api/workspaces/{id}/chats

The answer holds the chat's id. A workspace can have many chats. Each one keeps its own conversation, so a later message in the same chat can refer to earlier ones.

Send a message

curl -b "$ECHO" -N -X POST http://localhost:8000/api/workspaces/{id}/chats/{chat}/turns \
  -H 'content-type: application/json' \
  -d '{"prompt": "Create a small Vite site that says hello, build it and commit it",
       "credential_id": "your key id", "model": "claude-sonnet-5-5"}'

credential_id is the id of one of your keys, and model one of the model ids from GET /api/credentials/{id}/models. Each message names its key and model again, so you can move a chat to another model or provider at any message. The new model sees the whole conversation, but not the earlier model's hidden reasoning, which no other model can read. A key id that is not one of yours answers credential_not_found.

To choose how hard the model thinks, add "effort": one of auto, off, minimal, low, medium, high, xhigh or max. Higher levels help with hard tasks but are slower and cost more; off turns reasoning off where the model allows it. Without it the message uses auto, the level recommended for the model. Models take different levels, and one a model does not take answers effort_not_supported with the levels it does take. Keys for an OpenAI-compatible service take only auto.

The agent's reply streams back as it works, as server-sent events:

  • text: a piece of the agent's reply.
  • tool: the agent started using a tool, such as shell, read, write or edit.
  • done: the turn is over.
  • error: the turn stopped early. It has a code and, when the server failed, a request_id to quote when you report it.

A model id the key cannot use, or a key the provider has since revoked, makes the turn fail with turn_failed once it starts; check the list of models for the key.

Afterwards, look at what changed with the file and git endpoints on the Workspaces page.

What the agent knows about your project

Put an AGENTS.md file at the root of the workspace with your conventions, such as how to run the tests or which style to follow. The agent reads it at the start of every turn and keeps it up to date. Workflows it learns and scripts it writes for itself go in .agent/skills/ in the workspace, so it can use them again in later chats. It also keeps short notes about the workspace across chats.

Limits

  • One message at a time per chat. Sending another while the agent is still working gets the chat_busy error. Wait for done, or start a second chat.
  • A turn stops after 30 minutes (ECHO_TURN_TIMEOUT). Each command the agent runs stops after 2 minutes unless the agent asks for longer, up to 30 minutes.
  • Stopping curl stops the turn and the command that was running.
  • The agent cannot open a server it starts, such as a dev server, because the jail cannot reach localhost. It can build and test, and anything that runs to completion works.
