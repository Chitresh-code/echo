Workspaces

A workspace is a project folder with its own git repository. Everything that happens in it, including reading and saving files, runs inside that workspace's jail, so nothing in one workspace can reach another.

There is no editor in the browser yet. Until there is, you use workspaces through the API. Open the API reference and use "Try it out" on each endpoint, or call them with curl. The examples below assume Echo is on port 8000.

Create a workspace

curl -X POST http://127.0.0.1:8000/api/workspaces

The answer holds the new workspace's id, 32 letters and digits. Use it in every call below. A new workspace starts as an empty git repository with an .agent/skills/ folder, where the agent keeps the workflows it learns. GET /api/workspaces lists your workspaces, newest first.

Files

  • GET /api/workspaces/{id}/tree lists every file and folder, except the .git folder. It lists at most 5000 entries and says when it stopped short.
  • GET /api/workspaces/{id}/file?path=src/app.py reads a file. Text comes back as is; a file that is not UTF-8 text comes back base64 encoded, and the answer says which.
  • PUT /api/workspaces/{id}/file with {"path": "src/app.py", "content": "..."} saves a text file and creates any folders it needs.

Paths are always relative to the workspace, such as src/app.py. A path that starts with / or uses .. is refused. Files larger than 5 MB cannot be read or saved this way.

Git

  • GET /api/workspaces/{id}/git/status lists the files changed since the last commit, with git's status letters (M modified, D deleted, ? new and not yet added).
  • GET /api/workspaces/{id}/git/file?path=... returns a file as it was in the last commit and as it is now, for comparing the two. Either side is empty when the file did not exist there.

When something goes wrong

Every error answer has a code you can act on, such as file_not_found, invalid_path, file_too_large or workspace_not_found, and a request_id to quote when you report a problem.
