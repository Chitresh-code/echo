Using Echo

Connectors

MCP servers give your agent tools from outside its workspace, such as your issue tracker, error monitoring or a database. You connect a server once on the Connectors page, then turn it on for the workspaces that need it.

Two kinds of server

  • Remote, at a URL: a service that runs MCP on the internet, at an https address. Echo connects to it for the agent and keeps its sign-in to itself: the agent never sees the token.
  • Local, a command: a program such as npx -y @modelcontextprotocol/server-everything that Echo starts inside the workspace, in the same sandbox as the agent's own commands. A fresh copy starts for each reply.

Your servers are yours alone: nobody else signed in to Echo can see or use them. Header values, environment values and sign-in tokens are stored encrypted and never shown again; the page shows only their names.

Add a server

Connectors in the sidebar lists your servers. Add server opens a form. The name is lowercase letters, digits and underscores, and becomes the start of each of its tool names, so a linear server's tools show in the chat as linear_create_issue and the like.

For a remote server, give its URL and how it signs in:

  • None for public servers.
  • Headers for a server that takes a fixed token, usually an Authorization header with the value Bearer and your token.
  • OAuth for a server that signs you in at its provider. If the provider gave you a client id of your own, tick I have a client id from the provider and enter it, with its secret if it has one; otherwise Echo registers itself. Echo finds the provider's sign-in and token addresses in the details the server publishes (its OAuth metadata), and uses them only when they are https on the public internet. A server that publishes none cannot use OAuth; if its provider gives you an API token, choose Headers instead.

Echo connects to a server with no sign-in or with headers straight away and lists its tools, so a wrong URL or token is refused at once with what went wrong. An OAuth server is saved and waits for you to connect it.

For a local server, give the command and its arguments, one per line, and any environment variables it needs. The form shows the exact command line that will run.

A local server runs with the same access as the agent: it can read and change the workspace's files and reach the internet, so add only servers you trust. The agent can also read a local server's environment variables, so give it only keys you would give the agent itself. For tokens that matter, use a remote server, whose sign-in stays with Echo.

Connect and reconnect

Each server shows its status, and the button next to it says what it needs:

Ready
It works and its tools are listed under it.
Not connected, with Connect
An OAuth server you have not signed in to yet, or whose sign-in ended. Connect opens the provider's sign-in, and after you approve there you come back to Connectors with the outcome. A sign-in link works once and for 10 minutes.
Needs more access, with Reconnect
A tool asked for access you had not granted. Reconnect asks for the old and the new access together.
Tools changed, with Review tools
See below.

Replace headers or Replace variables sets new values, for example after a token expires. Delete removes the server, and every workspace stops using it.

Use a server in a workspace

Type /mcp in the message box to list your servers, with a tick on the ones the workspace uses. Pick one to turn it on or off; the list stays open so you can change several. Name and purpose in the workspace menu has the same list. A change applies from the next message. A workspace can use up to 10 servers.

The agent sees each server's tools like its own, with their descriptions. In Ask mode each call to a server's tool waits for your approval first.

When a server's tools change

A server writes its own tool descriptions, and the agent reads them. So Echo remembers the tools you saw when you added a server, and if the server later offers different ones, it leaves the server out of replies until you look. Review tools shows the new, changed and removed tools; Accept tools lets the server back in. Read changed descriptions with care: a description that tells the agent to do something unrelated to the tool is a warning sign.

When a server is not available

If a server cannot be used for a reply, the reply shows a line saying which server and why, and the agent is told so it can say what it could not do. The rest of the reply goes on. For a local server that exited, What the server said under the line shows the end of its error output. Common reasons:

It needs connecting, or needs more access
Connect or Reconnect it in Connectors.
It refused the sign-in
Its token is wrong or expired: replace its headers.
It did not answer within 20 seconds
The server is down or slow. Try again later.
It exited while starting
Check the command, its arguments and its variables against what the server prints.
The sandbox could not start it
A workspace runs at most 5 local servers, and they share the sandbox's process limit with background processes. Turn off servers the workspace does not need.

Limits

  • Up to 20 servers each, and 10 per workspace.
  • Remote servers must be on the public internet at an https address: a server on your own machine or office network is refused.
  • A tool call gets 120 seconds, and a result over 100,000 characters is cut short for the agent.
  • Echo uses only servers' tools, not their resources or prompts, and a server cannot ask you or the agent questions.
